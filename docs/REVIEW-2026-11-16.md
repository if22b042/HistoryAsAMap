## TL;DR

The site is in good shape: the security basics hold, the Python side has 223 tests, and
seven of the twenty improvements from the [8 November list](TOP-20-IMPROVEMENTS.md) are
built. What is left falls into three groups:

1. **Collection pages run one SQL query per entry.** A 60-entry collection costs 62
   queries per view; a full one (500 entries) costs 500 to 1,000. Half a day to fix.
2. **References are not stable.** Event addresses use the row id, which changes on every
   re-import; the daily game is recomputed from the live table; `sync-wikidata` does not
   update changed fields. These three share a cause and should be fixed together.
3. **Nothing limits abuse.** No rate limits, public collections go live at once, and the
   largest public collection is featured on the front page.

Two smaller bugs will be noticed by visitors: forms stop working after an hour
(B3), and quick filter changes can leave markers of the previous filter on the map (B2).

**How this was checked.** Read: all of `haam/*.py` and `haam/views/*.py`, `map.js`,
`game.js`, `timeline.js`, `events-data.js`, `collection-add.js`, `collection-map.js`,
`manage-entries.js`, `welcome.js`, `basemaps.js`, `event-picker.js`, the main templates,
`vercel.json`, `api/index.py` and the CI workflow. Not read in detail: `main.css`,
`tag-combobox.js`, `tag-picker.js`, `location-picker.js`, `haam/data/*`, the test bodies.
Run: an in-memory test app counting SQL queries per page, read-only SQL on
`instance/haam.db` (19,125 approved events), and the Leaflet.markercluster 1.5.3 source.
The browser was not used, so the interface bugs come from the code and are not reproduced.

**Legend:** ✅ = measured by running it · 📖 = certain from the code · ❓ = follows from
the code, not reproduced in a browser. Effort: **S** ≤ ½ day, **M** ≤ 2 days, **L** > 2 days.

### B1. One SQL query per entry on every collection page ✅

Measured with a 60-entry collection:

| Page | Queries |
|---|---|
| `/collections/<token>` | 62 |
| `/collections/<token>/map.json` | 122 |
| `/collections/<token>/map` | 62 |
| `/collections/` | 63 |
| `/api/welcome` | 63 |
| `/` (for comparison) | 2 |

At the 500-entry limit that is 500 to 1,000 queries per view. `/api/welcome` is the worst
place for it: the welcome card features the *largest* public collections
([welcome.py:57-68](../haam/welcome.py)) and reads `year_span` for each.

**Cause.** `CollectionEntry.event` is loaded lazily, once per entry
([models.py:282](../haam/models.py)). `year_span`, `all_wikipedia` and `all_confirmed`
walk every entry ([models.py:231-247](../haam/models.py)), and `to_map_dict` also loads
each event's tags ([models.py:374](../haam/models.py)). The admin collections page does
all of this for every collection, with no pagination
([admin.py:140-146](../haam/views/admin.py)).

**Fix.** Eager loading in `get_by_view_token` (entries → event → tags), SQL aggregates
for counts and year spans on list pages, pagination in the admin list.

**Done when** a 500-entry collection page runs fewer than 10 queries, and a test pins it.

### B2. Markers of the previous filter can stay on the map ❓

`applyFilters` calls `clusters.clearLayers()` and then `clusters.addLayers(...)` with
`chunkedLoading: true` ([map.js:1068-1082](../haam/static/js/map.js)). In
Leaflet.markercluster 1.5.3 a chunked `addLayers` works in 200 ms slices and re-schedules
itself with `setTimeout` (source lines 223-271); `clearLayers()` (lines 435-465) does not
cancel it. If a second filter change arrives while a large rebuild is still running, the
rest of the old set is added on top of the new one. The counter shows the new number; the
map shows more.

A rebuild of all 19k markers takes 0.3 to 0.5 s, so two category clicks in quick
succession, or typing in the search with a pause, should trigger it.

**Fix.** Queue the newest filter until the running batch reports done (the
`chunkProgress` hook is already used at [map.js:465-471](../haam/static/js/map.js)), or
build a fresh cluster group per rebuild and swap it in.

**Done when** a Playwright test clicks two categories 100 ms apart and the number of
markers in the cluster group equals the counter.

### B3. Forms expire after one hour ✅

`WTF_CSRF_TIME_LIMIT` is Flask-WTF's default of 3,600 seconds, and there is no handler
for `CSRFError`.

- "Add to collection" uses the token fetched when the map loaded
  ([collection-add.js:48-70](../haam/static/js/collection-add.js)). On a map left open
  for an hour every add fails with "Could not add the event. Reload the page and try again."
- An Add-event preview or a collection form submitted late gets Werkzeug's bare
  "Bad Request" page, and the typed text is lost.

**Fix.** `WTF_CSRF_TIME_LIMIT = None` (the token then lives as long as the session),
refetch the token after a 400 in `collection-add.js`, and a `CSRFError` handler that
shows the site's error page.

### B4. The daily game is not fixed for the day 📖

The five events are recomputed from the live table in each process and cached only in
memory ([game.py:257-274](../haam/game.py)). A guess is checked by round index
([views/game.py:108-110](../haam/views/game.py)).

- An approval, edit, deletion or sync during the day can change the set between two
  serverless instances, or between showing the puzzle and checking the guess. The guess
  is then scored against another event.
- The client notices changed titles and discards the saved progress
  ([game.js:604-611](../haam/static/js/game.js)).
- Past games and shared result links (`/game?date=…`) change with every data change.

**Fix.** A table `haam_daily_games` (date, hard, event references) filled on the first
request of the day, with a unique constraint so parallel cold starts agree.

### B5. Event addresses are not stable 📖

`/event/<id>-slug`, `/?event=<id>`, the sitemap and collection entries all use the row
id. `sync-wikidata` deletes and re-adds rows, and a fresh import renumbers everything.
An old link then returns 404, or lands on a different event: any slug is redirected to
the current one ([public.py:54-55](../haam/views/public.py)).

**Decision (16 Nov): use the Wikipedia page id.** `/event/<wiki_page_id>-slug` and
`?event=<page id>`. Every event in the current database has a page id. The map chunks
carry the page id as the event's id, so the JavaScript hardly changes. Old row-id links
redirect while the row still exists.

### B6. `sync-wikidata` never updates changed fields 📖

Only the category and the tags are compared
([importer.py:469-515](../haam/importer.py)). A corrected year, date, place, title or
summary in the CSV never reaches an existing row, although the README says the command
makes the database match the file.

**Fix.** Compare and update the scalar fields of imported events that no editor has
changed (`modified` is false).

### B7. No limit on years typed by people ✅

`parse_year_input("99999")` returns 99999 ([dates.py:230-245](../haam/dates.py), used by
`YearField` at [forms.py:31-37](../haam/forms.py)). The Wikidata export rejects future
years ([wikidata.py:191](../haam/wikidata.py)); the web forms do not. One approved event
dated 99999 stretches the year slider and the colour scale for everyone. In a collection
it does so for that collection's map, with no review.

**Fix.** Bound the year in `YearField`, for example 10000 BC to the current year.

### B8. No rate limits; spam can reach the front page 📖

Still open from TOP-20 #8.

- The editor login can be tried without limit.
- `/submit` makes outbound calls to Wikipedia and Wikidata on every request.
- Each practice game loads every candidate event and computes an HMAC per id
  ([game.py:175-199](../haam/game.py)); both endpoints are open and CSRF-exempt.
- Public collections are listed at once, and the welcome card features "most entries
  first" ([welcome.py:57-68](../haam/welcome.py)). A 500-entry spam collection goes
  straight to the front page until someone reports it.

**Fix.** Flask-Limiter with shared storage (Postgres or Upstash, since serverless has no
shared memory). Feature collections by an editor's flag, not by size.

### B9. `/api/events` is public, unused and expensive 📖

The old single-response endpoint loads all 19,125 events as ORM objects with their tags
on every call, with `max-age=60` and no CDN caching
([api.py:32-38](../haam/views/api.py)). Nothing on the site calls it: the map and the
event picker use the chunks. Remove it, or build it from the chunk code with CDN caching.

### B10. Wikipedia calls inside web requests can run ~45 s 📖

The shared client retries three times with back-off on a 10-second timeout
([wikipedia.py:71-73](../haam/wikipedia.py)), and a lookup makes two requests. It is used
by preview, by confirm (which looks the article up again) and by the link check for
custom entries. On Vercel a slow Wikipedia means a timeout page. Use a client with one
retry and a short timeout for interactive requests; keep the patient one for the CLI.

### B11. Add event still accepts non-events 📖

Still open from TOP-20 #9. `Article.dated_by_wikidata` is computed, but only the importer
reads it; `events.preview` ([events.py:122-128](../haam/events.py)) does not.

The website also takes the first Wikidata claim regardless of rank, deprecated ones
included ([wikipedia.py:149-154](../haam/wikipedia.py)), while the exporter uses
`_best_claims` ([wikidata.py:91-96](../haam/wikidata.py)). Use the exporter's function in
both places.

### B12. Events within a year are in alphabetical order ✅

The server sorts by year, then title ([feed.py:101](../haam/feed.py),
[collections_service.py:222-223](../haam/collections_service.py)), and so does the client
([events-data.js:77-81](../haam/static/js/events-data.js)). In 1944 "Battle of the Bulge"
(16 December) comes before "Normandy landings" (6 June): in the list below the map and,
more visibly, in a collection built from a tag, where the order is the story.

The `month` and `day` columns already exist ([models.py:124-125](../haam/models.py)).
Sort by year, month, day, title.

### B13. Production secrets are still in git history ✅

`.env.production` was added in commit `3972cab`. The file is no longer tracked, but it
can still be read from the history. I cannot tell whether the database password and the
Vercel token were rotated. If not, rotate them; then purge the history if the repository
is or was public.

### B14. Edit tokens fill the session cookie 📖

Carried over. Every collection's raw edit token sits in the signed session cookie
([collections_service.py:80-85](../haam/collections_service.py)). Past about 4 KB
(70 to 80 collections) the browser drops the cookie, and edit access to *all*
collections and the editor login go with it. The token is also part of the claim link's
path, so it reaches request logs and browser history.

### B15. Cache version has blind spots 📖

The tag part of the version fingerprint is a plain sum
([feed.py:51-55](../haam/feed.py)). Swapping tags between two events, or renaming a tag
to a name of the same length, leaves the version unchanged, and chunks are cached as
immutable for a year. It is rare, but when it happens nothing short of bumping `FORMAT`
clears it.

`state()` also runs about ten aggregates on every map page view. A version counter
bumped by every write path, cached in the process for a minute, fixes both.

### B16. Game storage grows without limit 📖

Every played day is kept in `localStorage` with its texts and answers
([game.js:604-611](../haam/static/js/game.js)). When the quota is reached, `saveStore`
swallows the error ([game.js:42-46](../haam/static/js/game.js)) and progress and streak
silently stop being saved. Keep the last 60 days.

### B17. Smaller issues 📖

- Shared tag and search links do not zoom to their events: `applyUrlFilters` never calls
  `zoomToTags` ([map.js:849-871](../haam/static/js/map.js)). TOP-20 #10.
- Opening an event uses `replaceState`, so Back leaves the site
  ([map.js:391-393](../haam/static/js/map.js)).
- Colour-by-year is linear ([map.js:54-59](../haam/static/js/map.js)); 15,910 of 19,125
  events are after 1500, so most share one hue. TOP-20 #11.
- Only 404 and 500 have error pages ([__init__.py:211-218](../haam/__init__.py)); 400,
  403, 405 and 429 fall back to Werkzeug's.
- The heatmap projects every shown event on each mouse move
  ([map.js:147-174](../haam/static/js/map.js)).
- Cluster icons call `getAllChildMarkers()` for every cluster
  ([map.js:114-139](../haam/static/js/map.js)).
- `Math.min(...years)` spreads ([timeline.js:370-373](../haam/static/js/timeline.js))
  throw above roughly 100k events.
- "Whole words only" builds a RegExp with a lookbehind
  ([map.js:752](../haam/static/js/map.js)), which throws on Safari before 16.4.
- An ongoing tag counts as a million-year span when the event page picks the "most
  specific" tag ([public.py:36](../haam/views/public.py)).
- Timezone-aware datetimes go into naive columns ([models.py:31-32](../haam/models.py));
  correct only while the database session's time zone is UTC.
- `import-csv` keeps the article's date label when the `year` column overrides the year
  ([importer.py:195-207](../haam/importer.py)).

### Checked and fine

No `innerHTML` with data; CSP and CSRF are in place; the login redirect guard holds; edit
tokens are stored hashed; Julian-calendar dates come through correctly (Hastings is
14 October 1066); a collection without entries does not start the map script.

## 2. Improvements

- **Search on the server** over the full summary (PostgreSQL `tsvector`, SQLite FTS5
  locally); the client intersects the returned ids with its filters. Finishes TOP-20 #1.
- **JavaScript quality.** About 4,500 lines with no tests, lint or types; `map.js` is one
  1,882-line module. Split it along its comment sections; share `formatYear`, `el` and
  year parsing (three slightly different regexes in `dates.py`, `map.js` and `game.js`);
  add ESLint and Playwright smoke tests. B2 is the kind of bug they catch.
- **Python tooling.** Only pyflakes runs. Add ruff, mypy, coverage, Python 3.13 and
  Dependabot.
- **Self-host the vendor scripts.** Leaflet, markercluster, heat and noUiSlider load
  without integrity hashes, and the CSP allows all of unpkg.com and cdnjs for scripts
  ([__init__.py:14-28](../haam/__init__.py)). With local copies it becomes
  `script-src 'self'`.
- **Deployment.** Every request, static files included, runs the Python function
  ([vercel.json](../vercel.json)), and each cold start checks the migrations under a
  lock. Serve static files from Vercel, migrate in a deploy step, and run the function
  in the database's region.
- **Operations.** No error tracking; `/api/health` does not touch the database; no
  documented backup. Collections are user data that no import can restore.
- **Audit trail and deletes.** Editor actions are not recorded. Deleting an event
  silently removes it from every collection ([models.py:147-149](../haam/models.py)).
- **Data model.** A unique (collection, event) constraint; a normalised country
  (752 free-text values today); `end_year`; an importance score.
- **Map tiles.** openstreetmap.org tiles are the default and are also hot-linked, 15 per
  event page ([seo.py:98](../haam/seo.py)), across 19k indexable pages. That is against
  OSM's tile usage policy.
- **Event pages.** Add schema.org `Event` data and a share image per event.
- **Editor tools.** Bulk approve and reject, search in the queue, duplicate and
  "year not in text" warnings, a tag admin page (the ToDo's "create new tags").
- **Accessibility** (TOP-20 #19). A skip link; markers out of the tab order.
- **Documentation drift.** The README's layout and API table miss `feed`, `game`, `seo`,
  `welcome`, `wikidata`, `tagging` and the chunk, welcome and game endpoints. In the
  `ToDo`, "FIX 1" (Teutoburg), deleting entries, event links and collections are done.
